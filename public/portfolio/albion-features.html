Feature map

길드 운영의 전체 흐름을
여덟 개 기능 영역으로 연결했습니다.

기능 하나를 고립된 화면으로 만들지 않고 신원, 권한, 이벤트, 보상, 경제, 통계, Discord, 운영 안전성이 서로 같은 규칙을 사용하도록 설계했습니다.

01
업무 신원테넌트 격리

온보딩·회원 신원·멀티테넌트

Discord 계정, 길드별 회원 기록, Albion 캐릭터를 분리해 로그인 방법이나 길드 이동이 과거 업무 이력을 바꾸지 않게 했습니다.

  • Discord OAuth와 봇 초대
  • 셀프서비스 길드 활성화
  • 안정적인 회원 UUID
  • 다중 길드 전환
  • 로컬 계정→Discord 연결
  • 길드 정지·삭제 생애주기
핵심 설계 판단

“여러 길드 지원”을 바로 구현하면 사용자·회원·캐릭터가 섞이므로, 필요한 접근과 금지할 데이터 합산을 먼저 정의했습니다.

02
행동별 상태원자적 변경

이벤트·파티·슬롯 운영

모집부터 운영 시작, 슬롯 배정, 실제 참가 확정까지 길드와 연합 참가자가 같은 이벤트 문맥에서 협업하도록 만들었습니다.

  • 파티·빌드 템플릿
  • 멀티 옵션 슬롯
  • 게스트 초대 링크
  • Discord 버튼 신청
  • 자동 운영 시작
  • 참가 일괄 마감
핵심 설계 판단

시작·종료 상태 하나로 모든 행동을 잠그지 않고 신청, 취소, 편집, 보상 snapshot의 허용 조건을 각각 정의했습니다.

03
인간 승인증거 보존

리기어 보상 자동화

킬보드와 이벤트 기록에서 보상 후보를 만들되 자동 지급하지 않고, 운영진이 증거와 정책을 검토한 뒤 확정하도록 설계했습니다.

  • 블랙존 자동 리기어
  • 항상 pending 생성
  • 부위별 가격 편집
  • 스크린샷·GIF 증거
  • 실버·제작 지급
  • 이벤트 정책 snapshot
핵심 설계 판단

자동화 속도보다 오지급 방지가 중요한 도메인이므로 자동 생성과 인간 승인, 원본 증거와 지급 결정을 분리했습니다.

04
원장 정합성멱등성

길드 상점·포인트·제작 경제

재고 조회에서 주문 예약, 관리자 확정, 수령, 포인트 원장까지 하나의 거래 흐름으로 연결했습니다.

  • 길드 재고 상점
  • 예약·취소·수령
  • 포인트 원장
  • 실버↔포인트 환전
  • 제작 작업 큐
  • 회원 간 거래
핵심 설계 판단

화면상 성공과 실제 재고·잔액 확정이 다르므로 DB 원자성, 재시도, Discord 알림까지 완료 범위에 포함했습니다.

05
원본 보존판정 projection

ZvZ 전투 집계·통계

Albion 전투 원본을 보존하면서 공식 교전, 상대별 matchup, 회원 성과, 공개 랭킹을 서로 다른 projection으로 만들었습니다.

  • 3개 서버 battle 수집
  • 20 vs 20 공식 교전
  • 상대별 matchup 분리
  • K/D·생존·참가 통계
  • 무기 카테고리 집계
  • 공개 ZvZ 분석
핵심 설계 판단

“큰 전투”라는 표현을 인원, 개입 상대, 집계 단위로 분해해 통계와 업적이 같은 판정 규칙을 사용하게 했습니다.

06
재시도중복 방지

킬봇·Discord 자동화

게임 이벤트 수집부터 카드 렌더링, 길드별 피드, 개인 DM, 관리자 알림까지 Discord 안에서 빠른 실행 흐름을 만들었습니다.

  • 킬·데스 카드 이미지
  • 지연 이벤트 보강
  • 길드별 피드 채널
  • 중복 전송 방지
  • 버튼형 빠른 실행
  • 사용자 언어 DM
핵심 설계 판단

누락을 UI 문제로 단정하지 않고 API 페이지, 수집 시간창, 아이콘 요청, 캐시를 각각 확인하고 실패 반례를 테스트로 남겼습니다.

07
언어 소유권접근성

다국어·접근성·사용자 경험

웹 화면과 Discord 알림의 언어 소유권을 분리하고, 관리자 화면까지 ko·ja·en·zh 메시지 동등성을 유지했습니다.

  • 4개 언어 동등 지원
  • placeholder parity
  • 개인 DM 언어
  • 길드 공용 언어
  • 모바일 운영 화면
  • 접근성 browser smoke
핵심 설계 판단

번역 누락 하나를 고치는 대신 개인·길드·공개 문구의 소유권을 정하고 전체 메시지 호출부를 자동 점검했습니다.

08
배포 계약회귀 검증

운영 안전·성능·배포

테넌트 격리, 마이그레이션 drift, 장애 복구, 브라우저 검증, 실제 운영 성능 측정을 제품 기능과 같은 수준으로 관리했습니다.

  • Postgres RLS·RPC
  • 안전한 DB push
  • migration drift gate
  • 운영 전후 성능 측정
  • Discord 장애 복구
  • 브라우저 matrix smoke
핵심 설계 판단

코드가 생성된 상태와 운영 가능한 상태를 구분하고, 타입·테스트·빌드·배포 확인을 완료 조건으로 고정했습니다.

Feature deep dives

화면 너머의 데이터와 정책까지
함께 해결한 대표 사례.

각 사례는 눈앞의 UI 수정에서 멈추지 않고 상태, 권한, 원자성, 실패 복구까지 같은 제품 규칙으로 연결했습니다.

02 · Event operations

상태가 아니라 행동별 불변식을 지시

이벤트가 시작된 뒤에도 늦은 신청은 가능해야 하지만 기존 신청 취소는 잠가야 했습니다. 하나의 status로 전체 화면을 비활성화하지 않도록 command별 허용 조건을 정의했습니다.

불변식 교정형
[시작됨] ≠ [모든 변경 금지]
신청 = 허용 · 취소 = 금지
게스트·회원·DB RPC가 같은 의미를 사용
구현late signup + frozen regear policy snapshot
증거migration 414 · commit 19f3fd7e
차이버튼 하나가 아니라 UI·action·RPC의 상태 의미를 함께 수정
03 · Regear

자동화와 지급 판단의 경계를 먼저 정의

게임 API만으로는 모든 파괴 원인을 확정할 수 없습니다. 자동화는 후보 생성까지, 금액 수정과 승인·지급은 운영진 책임으로 분리했습니다.

경계 탐색형 + 반례 고정형
자동 생성 = 허용
자동 지급 = 금지
증거 부족·OC 파괴·이벤트 정책 변경을 반례로 검증
구현pending 기본값 · 블랙존 한정 · 부위별 금액 · GIF 증거
안전성이벤트 시작 시점 정책 snapshot과 DB 쓰기 경계
차이자동화율보다 오지급 방지와 설명 가능성을 우선
05 · Battle analytics

모호한 ‘공식 전투’를 계산 가능한 규칙으로

전투 원본을 삭제하거나 상대를 하나로 합치지 않고, 홈 측 20명 이상과 개입 상대를 제외한 상대 전력 합계 20명 이상을 공식 교전 조건으로 정의했습니다.

불변식 교정형 + 경계 탐색형
원본 battle = 보존
공식 판정 = 별도 projection
상대 규모는 합산 · matchup은 분리
구현전투 grouping · matchup 상세 · 회원 성과 · 공개 랭킹
외부 제약Albion /battles API limit ≤ 51을 영구 규칙으로 관리
차이숫자 집계보다 판정 근거를 다시 열어볼 수 있게 설계
04 · Guild economy

화면의 주문을 원자적인 업무 흐름으로 확장

상품 선택에서 끝내지 않고 재고 예약, 가격 재검증, 취소, 관리자 확정, 수령, 포인트 원장까지 하나의 완료 계약으로 묶었습니다.

전체 흐름 완결형
사용자 주문 → 재고 예약 → 관리자 처리
→ Discord 알림 → 수령 → 원장 반영
재시도·중복 실행에서도 결과는 한 번
구현inventory reservation · atomic RPC · cancellation notification
성능서버 페이지네이션으로 /shop median TTFB 49.3% 감소
차이UI 성공과 DB 확정을 분리해 재고·잔액 정합성을 보호
End-to-end operating flow

여덟 개 기능은
하나의 운영 흐름을 공유합니다.

회원 신원을 기준으로 이벤트가 열리고, 참가 결과가 보상과 길드 경제에 연결되며, 전투 원본은 통계와 운영 개선으로 돌아옵니다.

Identity → Event → Reward → Insight

각 단계는 같은 guild_id, member UUID, event 정책과 감사 기록을 사용합니다.

  • 01 · IDENTITY회원 신원길드별 업무 주체와 권한
  • 02 · PLAN이벤트모집·편성·참가 확정
  • 03 · REWARD리기어증거·정책·인간 승인
  • 04 · ECONOMY상점·경제재고·주문·포인트 원장
  • 05 · INSIGHT전투 통계원본·판정·회원 성과
  • 06 · AUTOMATEDiscord공지·버튼·개인 알림
  • 07 · ACCESSi18n·UX4개 언어·모바일·접근성
  • 08 · OPERATE운영 안전격리·복구·배포 검증

공통 원칙 — UI 성공과 데이터 확정을 분리하고, 중요한 상태 변화는 DB 불변식과 감사 기록으로 다시 확인합니다.
