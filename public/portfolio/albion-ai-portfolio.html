Problem & ownership

화면을 모은 것이 아니라,
운영 전체를 하나의 데이터 흐름으로 설계했습니다.

모집에서 편성, 출석, 보상, 길드 경제, 전투 분석까지 같은 회원·이벤트·정책 데이터를 사용하게 만들었습니다. 자동화 속도보다 오지급, 데이터 혼합, 중복 실행을 막는 경계를 먼저 설계했습니다.

문제 정의

Discord 공지, 파티표, 스프레드시트 보상 기록으로 분절된 운영을 하나의 업무 흐름으로 재정의했습니다.

제품 설계

길드별 데이터 소유권, 이벤트 상태, 지급 승인, 원본 전투와 통계 projection의 경계를 결정했습니다.

엔지니어링

Next.js, Supabase, Discord, 외부 게임 API를 연결하고 마이그레이션·테스트·배포까지 직접 수행했습니다.

운영 검증

실패·재시도·중복 cron을 정상 조건으로 다루고 실제 운영 응답과 데이터 불변식을 완료 기준으로 삼았습니다.

AI는 실행 속도를 높였고,
제품 판단과 검증 책임은 제가 가졌습니다.

반복되는 제품 규칙은 저장소 문서와 테스트에 고정하고, AI에는 그 경계 안의 탐색과 반복 구현을 맡겼습니다. 생성된 코드의 채택 여부와 운영 배포는 제가 직접 판단했습니다.

01

로그인 계정과 업무 주체를 분리한 신원 모델

한 사용자가 여러 길드에 접근할 수 있어도 길드별 운영 기록과 캐릭터 이력은 섞이면 안 됩니다. 로그인 제공자인 Discord ID와 영속적인 회원 UUID를 분리해 계정 연결이나 길드 이동에도 과거 기록이 유지되게 했습니다.

문제한 Discord 계정의 다중 길드 접근과 길드별 업무 이력을 동시에 보호해야 했습니다.
판단로그인 제공자와 영속 업무 주체를 분리하고 회원 UUID를 기록의 소유자로 정했습니다.

02

이벤트 시작 후 신청과 취소의 의미를 분리

이벤트 시작은 편성을 보호해야 하지만 늦은 참가자까지 막아서는 안 됩니다. 신청은 허용하고 자기 취소만 잠그는 행동별 규칙을 정의해 회원·게스트·DB RPC·리기어 snapshot의 의미를 통일했습니다.

문제이벤트 시작 상태가 신청과 취소를 모두 막아 늦은 참가자를 받을 수 없었습니다.
판단상태명이 아니라 신청 허용·자기 취소 금지라는 행동별 규칙으로 분리했습니다.
구현회원·게스트 UI, action, 원자적 RPC, 리기어 정책 snapshot을 함께 수정했습니다.

설계 원칙

1
DB가 마지막 방어선

UI에서 숨기는 것과 서버·DB에서 막는 것을 분리하고, 중요한 불변식은 RPC와 제약조건으로 다시 확인했습니다.

2
원본과 해석을 분리

킬 로그와 전투 원본은 보존하고, 업무 판정과 화면 projection은 언제든 재계산할 수 있게 했습니다.

3
테넌트 경계를 타입처럼 취급

모든 주요 쿼리와 mutation에서 guild_id를 명시하고, 다른 길드의 행이 섞이는 반례를 통합 테스트했습니다.

4
배포 순서도 설계의 일부

호환 가능한 스키마를 먼저 추가하고 코드 전환 뒤에 레거시를 정리하는 expand/contract 방식을 사용했습니다.

5
운영 예외를 정상 흐름으로

API 지연, Discord 실패, 중복 cron, 재시도를 “특수 상황”이 아니라 기본 설계 조건으로 다뤘습니다.
