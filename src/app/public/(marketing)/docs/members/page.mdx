# 멤버 관리 & 길드 동기화

디스코드 길드원과 알비온 캐릭터를 1:1 로 묶고, 권한·상태를 관리하는 영역입니다. 한쪽에서 바꾸면 다른 쪽에 자동 반영되는 게 목표입니다.

## 사용 시나리오

- 새 길드원이 들어왔을 때 권한·상태를 부여
- 기존 멤버가 알비온 캐릭터를 변경/추가했을 때
- 게스트 (특정 이벤트만 보는 외부인) 를 임시로 초대할 때
- 알비온에서 길드를 떠난 사람을 정리할 때

## 사용법

### 멤버 목록 (`/members`)

- 사이트의 모든 멤버 카드 — 디스코드 닉네임 / 알비온 캐릭터 / 권한 / 마지막 활동
- 검색·필터: 이름, 권한 (admin / crafter), 인증 여부
- 카드 클릭 → 멤버 상세 (`/members/[discordId]`)

### 멤버 상세

- 알비온 캐릭터 정보 (서버, 길드, 명성, 장비 픽)
- 최근 트래킹된 킬/데스 (스크롤 가능, tracked 이벤트만)
- 청구 내역 / 보상 합계
- 어드민이라면 권한 토글 (admin, is_crafter), 멤버 비활성/제명 가능

### 알비온 식별자 페이지 (`/members/albion/[playerId]`)

알비온 player ID 로 직접 접근 — 디스코드 닉네임을 모르더라도 킬보드에서 해당 캐릭터의 활동을 추적할 수 있습니다.

### 길드 동기화

- 정기 동기화: Albion gameinfo API 의 길드 멤버 명단을 주기적으로 가져와 사이트 멤버와 매칭
- 떠난 사람: 알비온 길드에서 빠지면 사이트의 알비온 인증이 풀리고, 어드민이 일괄 정리 가능
- 새 사람: 알비온 길드에 추가됐지만 사이트 인증을 안 한 사람은 멤버 카드 없이 통계에만 잡힘

## 디자인 결정

### 왜 디스코드 ↔ 알비온 1:1 매핑인가

ZvZ 길드 운영의 모든 데이터 (청구·통계·업적) 는 한 사람당 한 줄로 정렬돼야 의미가 있습니다. 디스코드만으로는 알비온 활동을 못 보고, 알비온만으로는 청구를 못 합니다. 두 식별자를 하나로 묶어야 둘 사이의 데이터 (예: "이 사람의 이번 주 ZvZ 사망 → 청구") 가 자연스럽게 흐릅니다.

### 왜 게스트 시스템이 따로 있는가

연합 ZvZ 같은 이벤트엔 외부 길드원이 한 번 참여할 수 있어야 하지만, 그들에게 사이트 전체 권한을 줄 순 없습니다. 게스트는 `eventScope` 라는 토큰으로 자기 이벤트 페이지만 볼 수 있고 다른 URL 에 접근하면 자기 이벤트로 강제 리디렉트됩니다.

### 왜 인증 안 한 멤버도 통계에 잡히나

알비온 길드에는 가입했지만 사이트 인증은 미루는 사람이 항상 있습니다. 그들의 킬보드도 트래킹하지 않으면 길드 통계가 부정확해지므로, 알비온 길드 명단 기반으로 통계는 잡되 사이트 기능 (청구·상점) 은 인증한 사람만 쓸 수 있게 분리했습니다.

### 왜 `is_crafter` 가 별도 권한인가

제작 리기어 큐는 길드의 어드민이 아닌 "제작자" 가 잡고 처리합니다. 어드민 = 사이트 관리자, 크래프터 = 제작 담당이라는 두 역할이 보통 다른 사람이라, 어드민 권한과 분리해서 발급해야 권한이 비대칭으로 부풀지 않습니다.
