# 킬보드 트래킹

알비온 공식 gameinfo API 에서 길드원의 킬/데스 이벤트를 자동으로 가져와 사이트 데이터베이스에 누적하는 시스템입니다. 청구·통계·업적의 토대가 됩니다.

## 사용 시나리오

- ZvZ 후 사망자 자동 청구가 자동 생성되어야 할 때
- 멤버 상세 페이지에서 최근 활동을 보고 싶을 때
- 길드 통계·생존률·무기 사용 패턴을 집계할 때

## 사용법

### 자동 동기화

별도 조작 없이 백엔드가 정기적으로 알비온 API 를 호출해 길드원들의 신규 킬/데스를 가져옵니다. 사용자는 사이트에 들어와서 결과만 봅니다.

### 트래킹 범위

- **트래킹 대상**: 사이트 홈 길드 멤버의 kill 이벤트 (Killer 또는 Victim 이 길드원)
- **추가 정보**: 명성, 장비 슬롯별 itemId, 무기 카테고리, 사망 위치 (Zone)
- **저장**: `killboard_events` 테이블에 누적, 자동 리기어 매칭에 재사용

### 멤버 상세에서 확인

`/members/[discordId]` 의 "최근 킬/데스" 섹션은 트래킹된 이벤트만 노출하고 스크롤 가능합니다. 외부 킬보드 사이트와 다르게 길드 컨텍스트 (이번 주 청구 매칭, 업적 진행도 등) 가 같이 보입니다.

### 전투 상세 (`/battles/[id]`)

ZvZ 단위로 묶인 전투 화면에서는 참가자 카드 → K/D 요약 → 클릭 시 펼쳐지는 킬로그 (collapsible) 구조입니다. 한 번에 너무 많은 데이터를 펼치지 않습니다.

## 디자인 결정

### 왜 직접 트래킹 DB 를 두는가

알비온 공식 API 는 (1) 30분 정도 indexing delay 가 있고, (2) 과거 데이터 검색이 제한적이며, (3) limit 등 제약이 있습니다 (`/battles` 의 limit 은 51 이 상한). 모든 화면에서 매번 외부 API 를 치면 느리고 불안정하므로, 자체 DB 에 누적해서 기록·집계의 안정성을 확보합니다.

### 왜 30분 indexing delay 를 사용자에게 그대로 보여주나

자동 리기어가 청구 시 `verifyDeathInWindow` 로 길드/시간 매칭을 검증할 때, 너무 최근 사망은 알비온 API 에 아직 인덱싱되지 않아 매칭 실패 ("killboard 미검증") 가 일반적입니다. 청구를 거절하지 않고 "재확인" 버튼으로 사용자가 직접 다시 시도할 수 있게 둠으로써, 이게 시스템 결함이 아니라 알비온 측 지연이라는 걸 자연스럽게 노출합니다.

### 왜 무기 카테고리로 통계를 집계하나

같은 양손도끼(Halberd) 의 T7/T8/인챈트 다른 itemId 가 동시에 쓰입니다. 통계에서 이걸 모두 별개로 집계하면 "양손 도끼 사용 빈도" 같은 의미 있는 숫자를 못 뽑으므로, `extractWeaponCategory` + `stripTierPrefix` 로 카테고리 단위로 묶습니다 (AGENTS.md hard rule #7). 단, 킬 로그 자체는 원본 Type 문자열을 그대로 보존 — 사용자가 "정확히 어떤 장비로 죽었나" 를 보려고 할 때 손실되면 안 되니까.

### 왜 트래킹 슬롯이 6개인가

대상 슬롯: weapon, head, armor, shoes, offhand, cape. bag·potion·food·mount 는 일회성 소모재 또는 코스메틱 성격이라 청구·통계에 의미가 약합니다. 6개 슬롯만 깔끔히 트래킹해서 청구 시 실제 손실되는 장비에 집중합니다.
